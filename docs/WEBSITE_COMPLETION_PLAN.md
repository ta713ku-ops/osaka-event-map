## 1. 完成させる体験

**大阪の行きたいイベントが見つかり、日時・費用・参加方法を確認し、行く予定を決められるサイトにする。**

UIは祭りどころの写真の見せ方・回遊のしやすさを参考にし、情報はWalkerplusの網羅性と一件ごとの深さを比較基準とする。大阪に限定した探しやすさ、地図、公式根拠の明確さを独自の価値にする。

主な利用場面は「今日の行き先を探す」「今週末の予定を決める」「気になったイベントの参加条件を調べる」の三つ。スマートフォンを主対象とし、PCでも快適に利用できるようにする。

本書は実装の範囲・順序・完成条件を定める。当初は計画作成までを対象とし、その後のユーザー指示に基づき実装・データ更新・ローカル検証を行った。公開は工程5の指示後に実施する。

## 4. 全工程で守る方針

1. 日付・時刻・料金・予約・会場・座標・交通・雨天対応を推測で埋めない。
2. Walkerplusは掲載漏れを探す比較対象とし、本文・画像・イベント情報の転載元にしない。
3. 紹介文の要約は確認できた事実の範囲に限定し、推測の見どころ・所要時間・対象年齢を追加しない。
4. 画像は出典と利用条件を確認する。会場ロゴや汎用画像をイベント写真として扱わない。
5. 「開催期間中」「本日開催」「開催中」を区別する。休催日・離散日程・中止・受付終了を考慮し、「今夜」は明示された開始・終了時刻がある場合に限定する。
6. 収集失敗時の前回データは古い情報として識別し、確認日時を成功したように更新しない。
7. 既存の公開イベントIDを維持し、同じ催しの日程更新でリンクが不用意に変わらないようにする。

鮮度の初期基準は、今日・今夜の推薦対象を「最後の公式確認から48時間以内、かつ直近取得が成功」に限定する。取得失敗や期限超過のイベントは日程が有効なら一覧・詳細には残せるが、「本日開催」「開催中」と断定せず「掲載日程・最新状況は公式確認」と示す。別の有効期間が必要なソースは、工程1で更新頻度と理由を記録して個別に定義する。

## 5. 画面と情報の設計

### 5.1 ホーム

基本順序は「コンパクトな導入と検索入口 → 注目イベント → 今日・今週末のおすすめ → 目的・エリアから探す → 季節の特集 → 一覧・地図への案内」。

- サイト名・短い説明で役割を伝え、導入文と装飾だけで最初の画面を使い切らない。
- スマホ初期画面に、イベント名・画像・日程を読める注目カードと検索入口を置く。
- 「今日」「今週末」「無料」「エリア」など、利用場面から探せる導線を用意する。
- 注目枠は最大4件。候補不足時に弱いイベントで枠を埋めない。
- 季節の特集は、テーマに合う実イベントがある場合だけ表示する。遷移先にテーマ名・選定理由・対象一覧を用意する。
- 同じ会場ばかりを推薦しない。ただし多様性のために根拠の薄い候補を採用しない。
- 注目枠にあるという理由だけで、一覧の高順位から排除しない。

### 5.2 共通イベントカード

画像、イベント名、短い見どころ、日付、会場・エリア、確認できた料金、開催状態、保存ボタンを共通の順序で表示する。

長い公式タイトルと本文をそのまま詰め込まず、見どころは短く整理し、全文は詳細で読めるようにする。画像の比率と切り抜き位置を揃え、ポスター上に長文を重ねない。代替画像しかない場合は、日時・カテゴリを使った明示的な代替表示にする。

カード本体は詳細ページへのリンク、保存は独立したボタンとし、操作の入れ子や誤遷移を避ける。

### 5.3 イベント詳細

基本順序は「イベント名・写真・短い見どころ → 参加の基本情報 → 詳しい紹介 → アクセス → 関連イベント」。スマホでも参加条件を長文や関連カードの下に埋めない。

| 情報のまとまり | 表示内容 |
| --- | --- |
| 基本情報 | 開催日・時間・休催日・会場・料金・予約要否・開催状態 |
| 紹介 | 何を楽しめるか、公式根拠のある特徴、補足説明 |
| 参加方法 | 予約説明、存在する場合の公式予約リンク、問い合わせ |
| アクセス | 住所・最寄駅・確認済みの交通案内、地図、外部経路案内 |
| 注意事項 | 公式に明示された雨天・駐車場・変更事項 |
| 出典 | 公式URL、最終確認日時、前回取得情報である場合の表示 |

料金・時刻・予約が不明な場合は「情報未確認」と公式確認先を示す。任意の補足項目は不明欄を大量に並べない。無料タグだけで追加料金まで無料と解釈させず、料金条件を保持する。

予約先がある場合は「公式予約へ」、ない場合は「公式情報を確認」とし、経路ボタンも用意する。完売・受付終了の場合は参加可能と誤認するCTAを出さない。

### 5.4 検索・絞り込み

- キーワード、今日・今夜・明日・今週末・指定日、エリア、ジャンル、無料を組み合わせる。
- エリアは大阪市内の主要地域と府内地域から始め、データに根拠のある市区町村・住所で分類する。
- 選択中の条件・該当件数・個別解除・全解除を見える位置に置く。
- 無料・子ども向けなどの条件は、根拠があるイベントだけを対象にする。未確認を「有料」「不向き」と断定しない。
- 日付切替・検索・詳細から戻る操作で条件と一覧位置を保持する。
- 0件の場合は条件の解除や日付変更を案内し、条件外の結果を黙って混ぜない。
- 一覧は注目順・開催日順を提供し、取得した全件へ到達できるようにする。

### 5.5 地図・お気に入り

- 同一の確認済み会場をまとめる会場台帳を整備し、根拠URL・確認日・座標の確認方法を記録する。施設内の別棟・別会場は区別する。
- 未確認座標へ推測ピンを置かない。地図表示可能件数と座標未確認件数を分け、未確認イベントにも一覧から到達できるようにする。
- 初期位置が大阪駅などの固定基準なら、その基準を明示する。現在地取得を拒否しても利用できるようにする。
- 直線距離由来の分数はカードの主表示から外し、「直線距離」の表記と外部経路案内を基本にする。既存の時間条件を残す場合も概算であることを明示する。
- お気に入りは `routeId` をキーに端末内保存し、一覧・詳細・保存一覧で同期する。ログインや別端末同期は不要。
- 保存にはタイトル・開催日などの最小スナップショットも持たせる。収集対象から消えた項目は「最新情報を確認できません」、日付が過ぎた項目は「終了」と分け、勝手に削除しない。
- ストレージ無効・破損時も閲覧を続けられ、保存失敗はユーザーに伝える。

### 5.6 デザイン基準

既存のEditorialを基盤に、生成り・墨・朱・深緑を整理して使い、写真と日本語の読みやすさを主役にする。祭りどころのブランド・固有コピー・素材は複製しない。

余白、文字サイズ、画像比率、ボタン、状態表示を共通化する。自動カルーセルを残す場合は停止・手動操作・キーボード・動きを減らす設定に対応し、タップと縦スクロールを妨げない。

## 7. 情報充実の優先順位と測定方法

### 7.1 最初に深く整える対象

工程0で「今後30日以内に開催日のある大阪府内イベント」から、重点整備する30件を台帳に固定する。祭り・食・展示・体験・音楽を含め、大阪市内と府内の複数地域から選ぶ。話題性は無根拠に断定せず、公式内容と利用場面に基づいて選定理由を記録する。

Walkerplusの同期間の掲載と公式一覧から漏れを探す。各候補に、公式確認結果、掲載可否、未取得項目、次の調査先を付ける。公式で開催日・大阪会場を確認できない候補は公開対象に入れず、保留理由を記録する。

### 7.2 指標

上位表示の監査範囲は、ホームの全推薦枠と、今日・今週末それぞれの注目順上位20件（20件未満なら全件）とする。工程0でJSTの評価日時とデータを固定し、同一条件の改修前後を比較する。公開直前には最新データ・当日の条件でも再確認する。

| 指標 | 目標・扱い |
| --- | --- |
| 重点30件の調査 | 30件すべてについて、日付・会場・説明・料金・時間・予約・交通を調査し結果を記録する（必須） |
| 重点対象の公開 | 公開条件を満たす候補は掲載する。未掲載なら理由と対応を明記する（必須） |
| 確認済み基本情報の表示 | 重点対象で確認・取得済みの項目を取りこぼさず画面に表示する（必須） |
| 公開データの根拠 | イベント名・開催日・府内会場・公式URL・確認日時を全件で保持する（必須） |
| 重要な誤表示 | 日付・会場・料金の誤り、休催・中止の見落とし、代替画像の誤認を重点対象と上位表示で0件にする（必須） |
| 全体の説明保有率 | 80%以上を改善目標とする。文字数だけでなく内容をサンプル確認する |
| 全体の座標保有率 | 60%以上を改善目標とする。件数達成のための推測は禁止 |
| 料金・時間・予約 | 全件と重点対象の保有率をそれぞれ報告し、公式未公表と取得漏れを分ける |
| 掲載量・偏り | レコード数、同一催しの統合件数、会場数、地域・ジャンル別件数を併記する |

80%・60%は本計画で提案する改善目標であり、現時点の達成可能性は未検証。工程0で見込みを記録し、未達の場合は原因と残件を残す。必須条件と区別し、目標未達を達成扱いにしない。

## 8. 完成判定

### 8.1 利用シナリオ

| シナリオ | 合格条件 |
| --- | --- |
| 今日の行き先 | ホームから今日の候補を開き、開催日・料金・参加方法を確認できる。不明項目は不明と分かる |
| 今週末の予定 | 日付・エリア・ジャンルを組み合わせて比較でき、解除もできる |
| 地図から探す | 一覧と同じ条件が地図に反映され、座標未確認イベントの存在も分かる |
| 詳細から戻る | 条件・展開件数・スクロール・地図位置が復元され、ブラウザの戻る・進むも破綻しない |
| 保存して再訪 | 再読み込み後も保存が残り、解除・終了・データ消失・保存失敗を扱える |
| 個別URLを開く | 新規タブ・再読み込み・共有URLから同じイベントが開く。存在しないIDは回復導線を表示する |
| 障害時 | 読み込み中、取得失敗、画像切れ、検索0件、位置情報拒否でも次の操作が分かる |

### 8.2 画面・性能

- 390×844と1280×800で、ホーム・一覧・詳細・地図・保存一覧を確認する。実際のviewport寸法を記録し、設定が反映されていないキャプチャを証拠にしない。
- 横はみ出し、文字の欠け、固定ボタンによる本文の隠れがない。主要操作は44px以上を基本とする。
- キーボード操作、見えるフォーカス、適切な見出し・ラベル、通常文字4.5:1以上のコントラスト、動きを減らす設定を確認する。
- 同条件のモバイル計測を3回実施し、中央値でLCP 2.5秒以内・CLS 0.1以下を目標にする。達成値と測定環境を記録し、実利用者の性能値と混同しない。
- 画像の遅延読み込み・サイズ確保・データ転送量を見直し、主操作中に長い停止やレイアウト移動がないことを確認する。
- iPhone Safariの実機確認とデスクトップのブラウザ検証は別に記録する。実機を使えなければ「実機未検証」とし、端末対応まで完了とは報告しない。

### 8.3 検証・公開

実装内容に合わせて、日付境界・複数日程・料金0円・未確認値・分類・推薦・保存・履歴の回帰テストを追加する。単なる文言やCSS値を写すテストは増やさない。

必要な検証コマンドは `npm run typecheck`、`npm test`、`npm run test:collect`、`npm run audit:coverage`、`npm run audit:recommendations`、`VITE_BASE_PATH=/osaka-event-map/ npm run build`。ネットワークを使う監査とキャッシュ監査を区別し、失敗を成功に読み替えない。

公開前に静的詳細ページ、canonical・OGP・サイトマップ、既存URL、終了・欠落イベントの表示を確認する。公開指示後はCI成功だけで終わらず、公開サイトでデータ読込後のホーム・検索・詳細・地図・保存を確認し、新しいアセットが配信されていることを記録する。

不具合がある工程は未完了とする。公式未公表による情報欠損、改善目標未達、実機未検証は残課題として区別し、「必須条件を満たしたWeb版」と「未確認の範囲」を明示する。

| 一覧ページだけでは情報が薄い | 重点イベントから公式詳細を取得し、ソース別に欠損を記録する |
| 毎日の更新で推薦が再び偏る | 今日・週末の上位結果を記録し、販売・募集・同一会場の占有を点検する |
| 公式サイト変更・一時障害 | ソース別の失敗・前回成功日時を保持。古い情報を新着として扱わない |
| 終了イベントが収集から消える | 保存情報を残し、詳細URLの欠落時に一覧・代替候補への案内を出す |
| 画像不足・利用条件が不明 | 写真のないデザインで対応し、誤認を招く画像で埋めない |
| 見た目の改修で既存操作が壊れる | 個別URL・履歴復元・地図・絞り込みの回帰を工程ごとに確認する |

運営者向けの収集状況は詳細を確認できる位置に残し、利用者にはイベントごとの確認日時と必要な注意を簡潔に伝える。定期更新時には、収集失敗・重大な欠損増加・上位推薦の品質を確認できる記録を残す。
