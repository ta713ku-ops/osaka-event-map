## 1. 目的

公式情報のみを根拠とする現在の品質基準を維持したまま、大阪府内の公開イベント数と対応会場を増やし、WalkerPlus大阪版に近い規模の選択肢を提供する。

ここでいう「情報量」は、単なるJSONレコード数ではなく、次の三つを合わせて評価する。

1. 公開可能なイベント件数
2. 対応する自治体・会場・分野の広さ
3. 各イベントの説明、日時、料金、画像、予約情報など、公式に確認できる項目数

## 3. 実装しないこと

- WalkerPlusの本文、画像、日時、料金、紹介文を収集・転載しない。
- 会員ページ、認証API、アクセス制限、robots方針を回避しない。
- 不明な日付、会場、時刻、料金、座標を推測しない。
- 件数達成のために常設施設や通常営業をイベントとして水増ししない。
- 現在のデザインやナビゲーションを全面改修しない。
- 本計画の承認前に収集コードを実装しない。

WalkerPlusは、総件数・不足カテゴリ・不足会場を確認するベンチマークに限定する。候補を発見しても、主催者、自治体、会場などの公式ページで検証できるまで公開データへ入れない。

## 5. 実装フェーズ

### Phase 0: 基準固定と候補調査

実装前に、基準コミット、生成日時、公開件数、項目保有率、未対応会場、公開データ容量をスナップショットとして保存する。

各候補ソースについて次を記録する。

- 公式一覧URLと運営主体
- 公開形式（HTML、JSON-LD、公開JSON、RSS、ICS）
- 開催日、会場、詳細URLの取得可否
- ページ送り、休催日、複数日程、年またぎの表現
- 利用条件、robots、想定取得頻度
- おおよその公開可能件数

**完了条件:** 各ソースを `採用 / 保留 / 対象外` に分類し、採用理由とリスクが説明できる。

あわせて、同一対象期間でWalkerPlus側と自サイト側の件数を比較する。WalkerPlusの全件数を、そのまま取り込める公式イベントの数とみなさない。

### Phase 1: 高収量ソースの追加

優先度Aから、調査で安定性と件数を確認できた4〜7ソースを追加する。

既存の `scripts/sources/` 方式に合わせ、ソースごとに以下を実装する。

- 公式一覧の取得
- 日付、会場、公式詳細URL、公式画像の明示値のみを解析
- ソース固有の休催日・離散日程の保存
- DOM変更や0件化を検出する `recognized` 判定
- 小さな固定fixtureによるパーサーテスト
- 実取得件数と公開件数の分離

**中間目標:** 公開イベント430件以上、公開イベントを持つ公式収集元22件以上。

### Phase 2: 美術館・劇場・公演の追加

優先度B・Cから、公式スケジュールが安定しているソースを追加する。

同一公演の複数日・複数回は、公式の表現に応じて次のように扱う。

- 連続開催期間は1イベントとして保持する。
- 離散開催日は `schedule.dates` に保持する。
- 同日でも開演時刻が異なる公演は別イベントを維持する。
- ツアー名が同じでも会場または日程が異なる場合は統合しない。

**中間目標:** 公開イベント500件以上、公開イベントを持つ公式収集元27件以上、未対応主要会場8以下。

### Phase 3: 自治体拡張と詳細情報の補強

件数が不足する地域・カテゴリに限定して自治体公式ソースを追加する。同時に、一覧ページに不足する説明、料金、終了時刻、予約情報を公式詳細ページから補強する。

詳細取得は低並列度・タイムアウト付きで行い、一覧のイベントと公式URLで一対一に対応できる場合だけ統合する。詳細取得に失敗しても、一覧だけで品質ゲートを満たすイベントは公開を継続する。

**最終目標:** 公開イベント550件以上、公開イベントを持つ公式収集元30件以上、未対応主要会場5以下。

### Phase 4: 性能・UI・公開確認

データ増加によって一覧や検索を壊さないことを確認する。

- 初期表示は全件DOM展開せず、現在の段階表示を維持する。
- 検索、今日、今夜、明日、今週末、地図表示を確認する。
- 390×844と1280px幅で横はみ出し、操作不能、過度なレイアウト移動がないことを確認する。
- 画像失敗、0件、部分取得、stale状態を確認する。
- イベントJSONのgzipサイズを計測し、300KBを超える場合は説明文の別配信や遅延読込を検討する。

## 6. 収集・公開データフロー

```text
公式一覧を取得
  → ソース固有パーサー
  → 共通正規化
  → 日付・会場・公式URLの品質ゲート
  → 重複判定とprovenance統合
  → 鮮度・収集元別publishedCountの集計
  → coverage監査
  → events.jsonと詳細HTMLを生成
  → CI / GitHub Pages公開
```

収集元が失敗した場合は `error` または `stale` とし、成功0件へ変換しない。前回成功データの再利用上限は14日を維持する。

## 7. 変更予定箇所

実装時は主に次を変更する。

- `scripts/sources/`: 公式ソース別アダプターとfixtureテスト
- `scripts/sources/index.mjs`: ソース登録
- `scripts/lib/events.mjs`: 必要な場合のみ共通日時・正規化処理
- `scripts/collect-events.mjs`: 詳細取得やレポート項目が必要な場合のみ
- `data/source-registry.json`: 収集元と主要会場の対応付け
- `scripts/audit-coverage.mjs`: 地域・カテゴリ別不足の計測
- `public/data/*.json`: 実収集・監査結果
- `docs/SOURCE_COVERAGE.md`: 取得範囲と推測しない項目の記録

既存のUI変更は、件数増加による性能または操作上の問題が確認された場合に限定する。

## 8. テスト計画

### ソース単体テスト

- 通常のイベントカードを解析できる。
- 年またぎ、月またぎ、単日、連続期間、離散日程を区別できる。
- CMS公開日を開催日として使用しない。
- 休催日を開催日に含めない。
- 会場不明、日付不明、非公式URLのレコードを公開しない。
- ページ構造変更を成功0件として処理しない。

### 統合テスト

- live収集とcached buildでrouteId、件数、確認日時が安定する。
- ソース間重複ではprovenanceを失わない。
- 基準352件のうち、現在も開催対象で公式情報が有効なイベントを不必要に欠落させない。終了・中止・期限切れのイベントは維持を目的に残さない。
- 収集失敗時も正常な他ソースを公開できる。
- `publishedCount = 0` の収集元をhealthyにしない。

### アプリテスト

- イベント名・会場名検索
- 今日、今夜、明日、今週末
- 休催日と離散日程
- 座標のないイベントの一覧・詳細表示
- 詳細ページの公式URL、画像、関連イベント
- 390×844とデスクトップ幅

## 9. 各フェーズの公開判定

各フェーズは、次の条件をすべて満たした場合だけ統合可能とする。

1. 新ソースの運営主体と公式ドメインを確認し、取得範囲と制限が文書化されている。
2. 全テスト、型検査、production buildが成功する。
3. 公開品質ゲート違反がevents.jsonへ混入しない。
4. 重複群が0、または意図した別公演であることを説明できる。
5. 収集失敗・HTML変更・0件化がレポートに警告として現れる。
6. モバイルとデスクトップの実画面確認が成功する。
7. secrets、`.env`、認証情報が差分に含まれない。

最終フェーズでは、GitHub ActionsのCIとPages公開を完了させ、公開URLから次を直接確認する。

- 公開件数と収集元数
- 新しい公式ソースのイベント
- 生成済みイベント詳細ページ
- coverageとquality指標
- 実際に配信されているJavaScriptとJSON

## 10. ロールバック

- ソース単位で無効化できる構成を維持する。
- 問題のあるソースだけを前回成功データまたは警告状態へ戻す。
- 品質事故がある場合は該当公開コミットをrevertし、Pagesを再デプロイする。
- 他ソースの正常データやrouteIdを巻き戻さない。
- キャッシュを無期限に延命しない。

## 11. 主なリスクと対策

| リスク | 対策 |
| --- | --- |
| 公式サイトのHTML変更 | fixture、recognized判定、0件警告 |
| 件数優先による誤掲載 | 現行品質ゲートを変更しない |
| 同一イベントの重複 | 会場・日付・時刻・公式URLとprovenanceで判定 |
| 日程の誤った連続化 | `schedule.dates` / `closedDates` を使用 |
| 詳細ページへの過剰アクセス | 低並列度、タイムアウト、キャッシュ、一覧優先 |
| データ肥大化 | gzip計測、段階表示、必要時のみ詳細分離 |
| WalkerPlusとの数字だけの競争 | 公式根拠、分野・地域coverage、項目保有率も併記 |
| 利用条件・アクセス制限 | 公開入口のみ利用し、回避実装をしない |

## 12. 承認事項

実装開始前に、次の方針について承認を受ける。

1. WalkerPlusは転載元ではなく、情報量と不足分野のベンチマークに限定する。
2. 最終目標を「公式イベント550件以上、公開イベントを持つ公式収集元30件以上」とする。Phase 0で実現性を再評価する。
3. 優先度Aの主要施設から開始し、A → B/C → Dの順に拡張する。
4. 件数目標より公式根拠と誤掲載防止を優先する。
5. 各フェーズの品質ゲートを通過してから、最終的にmainへ統合・公開する。

計画の承認と実装指示を受けた後にPhase 0の調査から開始する。承認前は収集コード、公開データ、UI、GitHub Pagesを変更しない。

## 13. 実施結果

2026-09-21の最終検証では、既存の品質ゲートを緩めず、公開イベントを基準352件から563件へ増加できた。追加した公式収集元は、グランフロント大阪、なんばパークス、ルクア大阪、ビルボードライブ大阪、フェニーチェ堺、NHK大阪ホールの6件である。

| 指標 | 基準値 | 実施後 | 判定 |
| --- | ---: | ---: | --- |
| 公開イベント | 352件 | 563件 | 550件以上を達成 |
| 公開イベントを持つ公式収集元 | 16件 | 22件 | 30件目標は未達 |
| 主要会場の未対応 | 17会場 | 11会場 | 5会場以下は未達 |
| 会場根拠 | 100% | 100% | 維持 |
| 既知の重複群 | 0件 | 0件 | 維持 |
| 説明保有率 | 73.0% | 46.0% | 80%目標は未達 |
| 画像保有率 | 95.5% | 91.3% | 90%以上を維持 |
| gzip後のイベントデータ | 134,743 bytes | 182,322 bytes | 300KB以下 |

説明保有率の低下は、公式一覧が公演名・日付・会場だけを公開している音楽・舞台ソースを大量追加したことによる。説明を推測したり外部編集サイトから転載したりせず、空欄を正解として公開する。ソース数と主要会場の目標は、アクセス拒否、古いダミーページ、安定した開催日を得られない公式ページを無理に採用しなかったため未達とした。

大阪市立自然史博物館は最終収集時に取得できず、14日以内の前回成功データ2件を `stale` として使用している。他の22収集元は最新取得に成功した。画面確認で発見したZepp Nambaの貸切枠 `PRIVATE` は一般向けイベントではないため除外し、回帰fixtureを追加した。
