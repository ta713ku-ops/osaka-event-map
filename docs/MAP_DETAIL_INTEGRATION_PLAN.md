# 04｜地図とイベント詳細ページの統合 実装計画書

作成日：2026年9月23日

状態：実装・ローカル検証完了（2026年9月26日）

対象：どこいこ大阪 `/Users/taku/開発/地図`

## 1. 目的と今回の決定案

ホーム、通常一覧、地図のどこからイベントを選んでも、同じ公開URLの詳細ページを直接開く。地図の簡易モーダルを廃止し、詳細から戻ったときに探索を続けられる状態を維持する。

この文書は添付仕様「04_地図と詳細ページ統合.html」と現行コードのレビューを具体化した実装計画である。2026年9月26日に実装指示を受け、末尾に実施結果を追記した。

採用する案は次のとおり。

- 地図ピン、デスクトップの左側一覧、地図下部の候補カードから、簡易モーダルなしで詳細へ進む。
- 通常のイベント選択は履歴を1件追加する。関連イベントを開く場合も同じとする。
- ブラウザの戻る・進むと、画面内の戻るの整合性を保つ。
- 地図の中心・ズーム、検索条件、一覧の展開件数・スクロール、操作元のフォーカスを復元する。
- URL、イベントデータ、詳細ページの見た目、関連イベントの選定方法は維持する。

## 2. 現行コードで確認した事実

| 項目 | 現行の状態 | 今回の対応 |
| --- | --- | --- |
| イベントデータ | 地図も詳細も `data.events` を参照 | データ取得元を増やさず、既存データを継続利用 |
| 地図からの選択 | `selectedId` → `selectedSheet` → `EventSheet` | 3導線を共通の詳細遷移処理へ接続 |
| 詳細URL | `routeId ?? id` を使う `events/{id}/` | 既存の公開IDとBASE_URL対応を維持 |
| 詳細の履歴 | 開閉とも `replaceState` | 遷移時は `pushState`、復元情報の保存時は `replaceState` |
| スクロール復元 | `.app-shell.is-home` のみ明示的に復元 | 地図と詳細を含む履歴エントリー単位の復元に拡張 |
| 地図の保持 | 詳細表示中も探索画面を `hidden` で保持 | 通常遷移では継続。リロード時は保存状態から再構築 |
| モーダル背景 | EventSheet・絞り込み・プロフィールが共有 | EventSheet依存だけ削除 |

問題の中心は「地図だけ別の古いデータを取得していること」ではなく、地図に簡易詳細と別の選択状態が残っていることである。収集・更新処理の刷新は含めない。

既存の `docs/DETAIL_PAGE_POLICY_V3.md` は「地図→簡易プレビュー→詳細」を明記している。本計画が承認され実装される際に、該当する表示・遷移・受け入れ条件を更新する。その他の公式情報・デザイン・SEO方針は維持する。

## 3. 変更範囲

### 対象

- 地図ピン、左側イベント一覧、下部候補カードのクリック・キーボード操作。
- ホームと地図が共用する詳細遷移、履歴管理、表示状態・スクロール・フォーカスの復元。
- EventSheetと、それだけに使われる状態・型・DOM・CSS・テストの削除。
- 関連イベント遷移の履歴対応。選定ロジック・カードデザインは変更しない。
- 直リンク・リロード・未登録イベント・読み込み失敗時の既存表示の維持。

### 対象外

- 詳細ページや地図の全面的なデザイン変更、地図ライブラリの変更。
- 収集ソース追加、イベントの補完、画像重複対策、推薦や並び順の変更。
- 新しい地図専用URLや、検索条件をURLで共有する機能。
- 全タブ間の状態同期、ブラウザ終了後の探索状態の永続保証。
- ピンの重なり解消など、今回の導線変更に直接必要のない地図機能追加。

## 4. データとURLの契約

1. 全導線でイベントの内部 `id` を共通の遷移処理へ渡し、`data.events` の対応するイベントから公開ID `routeId ?? id` を決める。
2. URLは既存の `eventPath()` で生成する。同じイベントは選択元にかかわらず同じURL・同じ詳細内容になる。
3. 詳細の検索元は絞り込み後の一覧ではなく、全体の `data.events` とする。現在の検索条件に含まれないイベントも、直リンクから表示できる。
4. `routeId` の採番・移行・収集処理は変更しない。既存の内部IDによる復元互換性も維持する。
5. 座標の妥当性は既存の `hasCoordinates` に従う。ピンに出せないイベントも、通常一覧・地図側の一覧／候補・詳細からは除外しない。ただし既存の日付・検索・距離条件による絞り込みはそのままとする。
6. 未登録ID・不正なURL・読み込み失敗は既存の表示と復旧導線を維持する。日付・座標などを推測して埋めない。

## 5. 履歴と戻る・進むの仕様

### 基本原則

画面を新しく開く操作と、状態の保存を区別する。イベントを開くときは `pushState` で履歴を追加し、スクロールや地図位置の保存は現在のエントリーに対する `replaceState` で行う。`popstate` を処理しても履歴を追加しない。

| 操作 | 履歴・表示の結果 |
| --- | --- |
| ホーム／地図でイベントAを選択 | 元画面の状態を保存し、詳細Aを1件追加して表示 |
| 詳細Aで関連イベントBを選択 | Aの状態を保存し、詳細Bを1件追加して表示 |
| Bでブラウザまたは画面内の戻る | Aへ戻り、AのスクロールとBを開いたリンクへのフォーカスを復元 |
| Aでさらに戻る | 元のホーム／地図へ戻り、探索状態を復元 |
| ブラウザの進む | 元の詳細URLを表示し、当該エントリーに保存済みの状態があれば復元 |
| AまたはBでリロード後に戻る | 同じタブの履歴に保存した情報を使い、リロード前と同じ戻り先・状態を復元 |
| 外部サイト／ブックマーク／新規タブから詳細へ直アクセス | イベントをURLから復元。画面内の戻るはホームへ移動し、そのエントリーを置換 |
| 直アクセスした詳細でブラウザの戻る | ブラウザ本来の履歴に従う。外部サイトへ戻ることや、戻り先がないことを妨げない |
| 直アクセスした詳細Aから関連Bを開き、画面内で戻る | B→A。Aの画面内の戻るはホームへ移動 |
| 同じ詳細を再度選択／イベント選択を連打 | 同じ詳細URLの重複履歴を追加しない |
| 地図の余白をクリック／ドラッグ | 詳細への遷移も履歴の追加も発生しない |

画面内の戻るは「このアプリが同じタブ内で追加した、直前画面を持つ詳細エントリー」でのみ `history.back()` を使う。`history.length` やリファラーだけで判断しない。履歴の識別情報がない場合は直アクセスとして扱う。

ホームと地図の切り替え自体は、現行どおり新しい履歴を追加しない。現在の探索エントリーの表示モードを更新する。詳細ページのサイト名リンクは現行どおりホームへのリンクとして扱い、元の地図へ戻るボタンとは区別する。

## 6. 状態の保存・復元

### 保存先と寿命

`history.state` のアプリ専用キーに、バージョン付きの復元情報を保存する。既存の他のキーは上書きしない。DOM要素やイベント全件などは保存せず、識別子と表示復元に必要な値だけを保持する。

各エントリーには一意のID、画面種別、詳細の場合の公開ID、アプリ内で作成した直前エントリーのIDの有無を持たせる。初期表示時にはURLを画面種別の基準とし、URLと合わない・壊れている・未知のバージョンの復元情報は採用しない。

同一タブの戻る・進む・リロードを復元対象とする。別タブで開いたURLには元タブの地図位置などを引き継がない。

### 保存する表示情報

| 画面 | 保存内容 |
| --- | --- |
| 探索画面共通 | home／map、検索語、日付条件、詳細フィルター、距離計算に使っていた起点・表示名 |
| ホーム | スクロール位置、選択元イベントIDと導線種別 |
| 地図 | 中心座標・ズーム、左側一覧のスクロール、下部候補の横スクロール、両一覧の展開件数、選択元イベントIDと導線種別 |
| 詳細 | 公開ID、詳細スクロール位置、戻った際にフォーカスする関連リンクのイベントID・セクション |

距離計算の起点と地図の表示中心は別の値として保持する。リロードによる復元で位置情報の取得や許可要求を自動実行しない。絞り込み・プロフィール・経路選択のダイアログ開閉状態は復元せず、閉じた状態にする。プロフィールの保存方式は現行を維持する。

スクロールや中心位置などは変更を間引いて現在のエントリーへ保存し、画面を離れる直前にも確定する。保存処理を毎フレーム呼ばない。

### 復元の順番

1. URLと履歴情報から、表示する画面とイベントを決定する。
2. 検索条件、起点、表示モード、展開件数を復元する。
3. イベントデータと対象DOMが利用可能になってから、地図の中心・ズームとスクロールを復元する。
4. 地図を再表示した際はLeafletのサイズを再計算し、空白やずれが出ないことを確認する。再計算で中心・ズームを初期値へ戻さない。
5. 最後に操作元へ `preventScroll` 付きでフォーカスを戻す。

固定時間の待機で復元せず、描画・データの準備状態を基準にする。復元途中の初期値を保存して、保存済み状態を消さないようにする。

新しく詳細を開いた場合は先頭から表示して見出しへフォーカスする。履歴から詳細へ戻った場合は保存済みのスクロール・操作元を優先し、現行の見出しフォーカス処理が復元を上書きしないよう調整する。

イベント消失・絞り込み結果の変化・画面幅変更により復元先がなくなった場合は、スクロールを有効な範囲に収める。フォーカスは地図の操作可能なコンテナ、一覧の見出し、詳細の見出しなど、その画面の安定した要素へ戻す。存在しないイベントを選択状態として残さない。

## 7. 地図選択と旧UIの整理

- ピン、左側一覧、下部候補カードをすべて共通の詳細遷移処理へ接続する。
- `EventMap` のコールバックはイベント選択だけを通知する契約に整理する。地図の余白クリックから `null` を渡す旧選択解除処理は不要になる。
- `selectedId`、`selectedSheet`、EventSheet専用の `selected` 計算・クラス・分岐を削除する。地図の選択IDをフォーカス復元用のIDとして流用しない。
- 候補カードの表示条件に残る旧 `selected` 依存を除去する。既存のイベント0件表示は維持する。
- EventMarkerの選択時拡大・選択ラベルなどは参照元を確認して整理する。通常のピン表示・既存の常時表示ラベル・開催状態の表現は維持する。
- Enter／Spaceなど既存のキーボード選択を維持し、キーイベントとクリックの重複で履歴が二重追加されないよう確認する。地図へのフォーカス復帰も実際のLeaflet DOMで検証する。
- EventSheetコンポーネント・専用テストは、他の呼び出しがないことを確認して削除する。
- `.modal-scrim` は絞り込み・プロフィール用に残す。`.event-sheet, .filter-sheet, .profile-dialog` のような共有CSSは、EventSheetのセレクターだけを外す。
- 経路案内の共通関数にある旧選択イベントへの依存を外し、詳細ページから渡されたイベントで従来の経路URLを開く。

既存の `eventRoutes` や静的詳細HTML生成は原則維持する。変更が必要になった場合も公開URLを変えず、理由と差分を報告する。並行して詳細ページの変更がある場合は、実装開始時の最新版を確認し、そのデザインを上書きしない。

## 9. 検証計画と合格条件

### 自動テスト

| 検証 | 合格条件 |
| --- | --- |
| 3導線の直接遷移 | EventSheetを表示せず、対象詳細が開く |
| 同一イベントのURL | ホーム・通常一覧・地図3導線でURL・内容が一致。`routeId !== id` のデータでも成立 |
| 履歴 | 正常遷移は1回だけpush、状態保存はreplace、popstateでpushしない |
| 戻る・進む | 地図→A→B→戻るA→戻る地図→進むA→進むBが成立 |
| リロードと直アクセス | 有効な履歴情報の再読込と、情報のない直アクセスで戻り先を区別 |
| 復元情報の異常 | 未知バージョン・欠損・URL不一致を安全に無視 |
| 座標なし | ピンだけを除外し、一覧・候補から詳細が開く |
| URL・例外表示 | BASE_URL配下のURL、既存ID互換、未登録ID、読み込み失敗と再試行を維持 |
| 周辺機能 | 絞り込み・プロフィールの背景と閉じる操作、詳細の外部経路リンクが正常 |

`App.test.tsx` にある「pushStateを呼ばない」「画面内の戻るでhistory.backを呼ばない」という旧契約のテストは、新しい遷移表に置き換える。履歴情報がない詳細のホームへのフォールバックは別ケースとして残す。

実装後の必須コマンドは `npm test`、`npm run typecheck`、`npm run test:collect`、`VITE_BASE_PATH=/osaka-event-map/ npm run build` とする。ビルドはcached収集・coverage生成を含むため、生成差分を確認し、今回の変更と無関係なイベントデータの更新を混在させない。

### ブラウザでの操作確認

390×844と1280×800の両方で、次を確認する。Leafletをモックしたコンポーネントテストだけでは合格にしない。

1. 地図を移動・拡大し、検索・日付・条件を設定してからピン→詳細→戻るを繰り返す。
2. PCは左側一覧をスクロールし、モバイルは下部候補を横スワイプして詳細を開く。「もっと見る」で増やした件数も復元されることを確認する。
3. ブラウザの戻る・進むと、画面内の戻るをそれぞれ操作する。関連イベントを経由し、詳細でリロードしても同じ順序で戻れることを確認する。
4. 直リンク・別タブ・未登録IDからの画面内の戻る／イベントを探すが、存在しない地図状態を復元せずホームへ進むことを確認する。
5. キーボードでピン・一覧・関連リンクを選択し、詳細の初期フォーカスと戻った際の操作元を確認する。フォーカス移動による不要なスクロールを起こさない。
6. リロード後の復元をデータ読み込みが遅い条件でも確認し、地図の空白、初期位置への巻き戻り、横はみ出し、旧モーダルの残存がないことを確認する。
7. イベントが更新・消失した場合や、画面幅を変えた場合に、復元失敗で操作不能にならないことを確認する。
8. コンソール例外、アプリの通信失敗、地図タイルの読み込み失敗を確認する。外部サービス由来の失敗はアプリの例外と分けて記録する。

ブラウザ検証は実機のiPhone Safari・iPad Safari・VoiceOver確認と区別して報告する。実機を操作していない場合は「実機未確認」と明記し、「実機相当確認済み」とまとめない。

### 公開確認

公開まで依頼された段階で、コミット・push・CI・Pagesデプロイ・公開URLを確認する。公開アセットに変更が含まれること、公開詳細URLの直リンクとリロード、地図→詳細→戻るを確認して公開完了とする。HTTP 200やActions成功だけでは完了扱いにしない。

## 10. 完了の判定と成果物

実装完了の条件は、地図3導線からの直接遷移、遷移表どおりの履歴、探索状態とフォーカスの復元、座標なしイベントの維持、旧UIの安全な削除、自動テスト・2画面サイズのブラウザ確認がすべて成立すること。

成果物はコード差分、更新した方針文書、テスト結果、ブラウザ操作の確認結果とする。実機確認と公開確認は実施範囲を別記し、未実施を明示する。

## 11. 実施結果（2026年9月26日）

- 地図3導線の直接遷移、履歴・復元、旧UI削除と既存方針の更新を実装した。
- ホーム側も深いスクロール位置へ戻れるよう、展開件数を復元情報に含めた。
- スクロール直後のブラウザ戻るでは、離れた履歴エントリーを直接更新できない。このため最終位置だけを同じタブのsessionStorageへ補助保存し、当該履歴への復帰時に書き戻して補助データを削除する。ストレージが利用できない場合は履歴とメモリの復元へフォールバックする。
- 失敗・読み込み中のDOMで保存位置を上書きしないよう、イベントデータが取得できるまで復元を保留する。再試行成功時に保存位置へ戻す。
- 親による差分レビュー、自動テスト、本番用ビルド、実ブラウザの390×844・1280×800確認を実施した。
- 詳細な証跡と確認範囲は [MAP_DETAIL_INTEGRATION_VERIFICATION.md](./MAP_DETAIL_INTEGRATION_VERIFICATION.md) を参照。
- コミット・push・公開は未実施。iPhone/iPad実機・VoiceOverは未確認。
